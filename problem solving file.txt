২.৮  PHASE 4 — যে "recovery" আসলে কিছুই করত না
--------------------------------------------------------------------------------
পুরোনো code (site/assets/js/app.js):

    try { if (state.mpegts) { state.mpegts.load(); state.mpegts.play(); } }
    catch (_) {}

mpegts.js একটি ইতিমধ্যে-loaded player-এ load() **উপেক্ষা করে** — আগে
unload করতে হয়। অর্থাৎ এই পথটি প্রতিটি log-এ recovery হিসেবে দেখা যেত এবং
প্রতিটি run-এ ছিল সম্পূর্ণ নিষ্ক্রিয়। আর যা-ই ভুল হোক, exception খালি
catch-এ হারিয়ে যেত।

যা করা হলো — নতুন recreateMpegTsPlayer():
  • পূর্ণ teardown ও পুনর্নির্মাণ:
    pause → unload → detachMediaElement → destroy → create → attach
    → load → play
    প্রতিটি teardown step আলাদা করে guarded — একটি errored player pause()-এ
    throw করতে পারে অথচ তখনও unload/destroy দরকার, নইলে প্রতি attempt-এ
    একটি worker ও SourceBuffer leak হয়
  • LOADING_COMPLETE handler — raw-TS "live" route যে finite body দিয়ে
    clean EOF-এ শেষ হয় (মাপা: ১০.৬ MB, direct ২.৪৬s / proxy ৪.৪৬s,
    ৬০s probe-এর বিপরীতে) সেটি এখন ধরা পড়ে। আগে stream থেমে যেত আর
    player-এর কিছুই জানত না যে source শেষ, তাই কোনো recovery চেষ্টাই হত না।
    movie শেষ হওয়া স্বাভাবিক, তাই movie বাদ।
  • bounded retry — সর্বোচ্চ ৪ বার, exponential backoff (৮০০ms × 2^n)
  • duplicate-burst সুরক্ষা — stall watchdog, error handler ও
    LOADING_COMPLETE তিনটিই একই ঘটনায় fire করতে পারে
  • exception আর গিলে ফেলা হয় না — failCurrentAttempt()-এ যায়, যাতে
    attempt ladder পরের route ধরতে পারে
  • সত্যিকারের সফল playback-এ retry budget ফিরে আসে — নইলে budget একবার
    খরচ হয়ে আর কখনো ফিরত না, এবং যে channel সন্ধ্যায় চারবার recover
    করেছে সে পঞ্চম hiccup-এ বাদ পড়ত

test: tests/test_player_recovery_contract.py (১৩টি)। একটি test সরাসরি
পুরোনো no-op-এর আকৃতি খোঁজে, তাই ওটা ফিরে এলে test fail করবে।

১। দ্বিতীয় VANTAGE — এখনো মাপা হয়নি

   আগে ভুল কারণ লিখেছিলাম ("আলাদা network দরকার")। মেপে দেখা গেল সঠিক
   কারণ আলাদা:
     vantage 1 (scanner egress)  AS8075 Microsoft Corporation, country IN
     vantage 2 প্রার্থী            Cloudflare worker (ভিন্ন ASN)

   worker দিয়ে নিজের egress মাপার চেষ্টার ফল:
     Origin header ছাড়া   → "Playback requires the Click TV site origin"
     site origin দিয়ে      → "Target host not allowed"

   অর্থাৎ proxy-র একটি বন্ধ host allowlist আছে (data/allowed-hosts.json,
   ৪২১টি host) এবং api.ipify.org তাতে নেই। এটি ভালো নকশা।

   **আমি allowlist খুলিনি।** একটি measurement চালানোর জন্য proxy-র
   security allowlist শিথিল করা খারাপ বিনিময় — proxy-টি ঠিক এই কারণেই ওই
   তালিকা রাখে।

   ফলাফল: may_hide()-এর "দুটি measurably independent vantage" শর্ত
   পূরণযোগ্য নয়, তাই ওই কঠোর guard বাস্তবে কিছুই hide করতে দেয় না।
   এই মুহূর্তে সেটিই সঠিক আচরণ।

   দুটি পথ (দুটিই infrastructure পরিবর্তন, measurement নয়):
     ক) worker-এ একটি /egress endpoint যোগ করা যা নিজের বেরোনো IP/ASN
        জানায় — allowlist অপরিবর্তিত থাকে, এটিই নিরাপদ পথ
     খ) allowlist-এ একটি IP-echo service যোগ করা — সহজ, কিন্তু proxy-র
        security posture শিথিল হয়

৩। keyframe_verdict এখনো অগম্য

   Phase 0b-র lock বলে ১০ সেকেন্ড media clock-এর নিচে সব keyframe রায়
   `unknown`, আর বর্তমান 16 KiB probe এক intra interval-এর ২.৮% — অর্থাৎ
   ওই floor ছোঁয়াই সম্ভব নয়। এটি ফাঁক নয়, lock-এর নির্দিষ্ট আচরণ:
   "the existing 16 KiB probe can never produce a keyframe verdict.
   It stays a reachability probe only."

৪। Zee Bangla-র stutter-এর প্রকৃত মেরামত

   কারণ প্রমাণিত (interlaced + শূন্য IDR), channel সুরক্ষিত (কখনো hide
   হবে না), কিন্তু ছবি এখনো আটকায়। এর জন্য দরকার interlaced/no-IDR
   stream-এর জন্য ভিন্ন player handling, অথবা ওই source-এর একটি

৫। ২১১টি blocked movie সম্পর্কে কোনো সিদ্ধান্ত
