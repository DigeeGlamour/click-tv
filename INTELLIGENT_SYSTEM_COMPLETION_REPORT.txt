২. PERSISTENCE COUNTER — Correction 3 সম্পূর্ণ implement
--------------------------------------------------------------------------------
আগে শুধু `PERSISTENT_UNAVAILABLE_CANDIDATE` নামের constant ছিল, কোনো logic
ছিল না। এখন দুটি function:

  resets_persistence(observation)   — কোনটা "full sustained success"
  persistence_state(observations)   — counter কখন candidate-এ পরিণত হয়

reset শুধু দুটি জিনিসে হয়:
  • পূর্ণ ১২০s PASS (startup ≤১০s, media progress ≥১১৫s, cumulative stall
    ≤৫s যেখানে stall = ১s sampling-এ >২s স্থবিরতা, শূন্য fatal error,
    প্রতিটি announced render track এগিয়েছে), অথবা
  • সমান দীর্ঘ ও অবিচ্ছিন্ন media delivery (browser session না থাকলে)

যেগুলোতে reset হয় **না** — নাম ধরে ধরে বাতিল:
  • HTTP 200
  • manifest / playlist fetch সফল
  • ছোট byte sample সফল (বর্তমান 16 KiB probe সহ)
  • পূর্ণ window-এর চেয়ে ছোট যেকোনো observation
  • startup শুরু হয়ে window-এর ভেতরেই fail

কেন এতটা কঠোর: চারটি hidden channel-এর primary এই vantage থেকে HTTP 200 ও
বৈধ ছোট manifest ফেরত দেয়, অথচ ledger-এ failed_player_twice হিসেবে আছে।
আলগা reply নিয়ম থাকলে ওই 200-ই counter চিরকাল reset করে রাখত।

৬. ZEE BANGLA — আসল browser-এ ১২০ সেকেন্ড চালিয়ে মাপা কারণ
--------------------------------------------------------------------------------
এই প্রথম Zee Bangla-র উপর পূর্ণ ১২০ সেকেন্ডের measurement চালানো গেছে।
harness site-এর **নিজের** buildAttemptPlan() ও buildProxyUrl() ব্যবহার করে,
তাই যে URL, proxy আর player config মাপা হয়েছে সেগুলোই একজন দর্শকের browser
ব্যবহার করে — আমার বানানো কোনো আলাদা player নয়।

মাপা ফলাফল (real Chromium, proxy route, mpegts.js, ১২০টি sample):

  announced render tracks     video + audio   (MEDIA_INFO থেকে)
  progressing tracks          audio মাত্র
  video frame decoded         ০  (webkitDecodedFrameCount ১২০ সেকেন্ডেও ০)
  audio decoded bytes         ৩৮৪  (অর্থাৎ audio ঠিকই আসছে ও decode হচ্ছে)
  first frame                 ৪.৪২s
  media progress              ০.০৮s   (১২০s-এ মাত্র ০.০৮s এগিয়েছে)
  cumulative stall            ১২০s
  fatal error                 media element error code 3 = MEDIA_ERR_DECODE
  তারপর বারবার                MediaMSEError code 11 — appendBuffer ব্যর্থ,
                              কারণ HTMLMediaElement.error আর null নয়

অর্থাৎ **route মরা নয়, byte-ও ঠিকঠাক আসছে — browser video decode করতে
পারছে না।** এটি Phase 0-র structural finding-এর সঙ্গে হুবহু মেলে:
১৯২০x১০৮০ **interlaced** H.264 (frame_mbs_only = 0), **শূন্য IDR frame**,
শুধু open-GOP I-slice। MSE-তে Chromium interlaced H.264 decode করে না, আর
IDR ছাড়া decode শুরু করার বৈধ random-access point-ও নেই।

এতেই "atka atka" আসল কারণ ধরা পড়ে: audio চলে, video আটকে থাকে।

**এবং এই measurement আমার model-এ একটি আসল bug ধরিয়ে দিয়েছে।**
classify_playback() এই ফলাফলকে `playback_fail` বলছিল, যা escalatable —
অর্থাৎ যথেষ্ট evidence জমলে Zee Bangla hide হয়ে যেতে পারত। কিন্তু decode
করতে না পারা একটি **browser-এর সীমাবদ্ধতা**, route-এর দোষ নয়। ঠিক করা হলো:

  decode/capability failure → advisory:device_or_browser_unsupported
    • escalatable নয় (কখনো hard_disqualified হতে পারে না)
    • সর্বোচ্চ scope = environment:<profile>, কখনো global নয়
    • ১২ বার পুনরাবৃত্তি করলেও persistence counter এগোয় না
    • চারটি profile-এ global-scoped evidence দিলেও may_hide() না বলে

৮টি test দিয়ে এই আচরণ বাঁধা হয়েছে, এবং একটি test উল্টো দিকও পাহারা দেয় —
সত্যিকারের route failure (কোনো decoder signature নেই, কিছুই এগোয়নি) এখনও
`playback_fail` এবং এখনও escalatable।

  probe-এর সবচেয়ে জরুরি ফল, এবং এটি আমার আগের ধারণা সংশোধন করে:
  **H.264 High 4.0 এই browser-এ সমর্থিত** (avc1.640028 → হ্যাঁ)। অর্থাৎ
  Zee Bangla-র decode ব্যর্থতা codec profile-এর কারণে **নয়**।
  ব্যর্থতা এমন স্তরে যা isTypeSupported() প্রকাশই করতে পারে না —
  interlaced macroblock coding (frame_mbs_only = 0) এবং শূন্য IDR frame।
  isTypeSupported শুধু codec string যাচাই করে, frame structure নয়; তাই সে
  "হ্যাঁ" বলে অথচ প্রকৃত decode ভেঙে পড়ে। দুটি পর্যবেক্ষণ একসাথে রাখলে
  ছবিটা সম্পূর্ণ হয়: codec চলে, কিন্তু এই stream-এর frame structure চলে না।

  আরও যা মাপা হলো (উভয় engine-এ):
    audio/mpeg (bare)            → হ্যাঁ
    audio/mpeg;codecs="mp2"      → না
    video/mp2t (যেকোনো রূপে)      → না  (তাই mpegts.js-এর remux অপরিহার্য)
    HEVC (hvc1/hev1)             → Chromium-এ না, WebKit-এ হ্যাঁ
                                    (beIN channel-গুলোর জন্য প্রাসঙ্গিক)

  এই probe শুধু এই browser build সম্পর্কে বলে। তাই এখান থেকে পাওয়া
  "না" কখনো stream নষ্ট হওয়ার প্রমাণ নয় — model এটিকে
  advisory:device_or_browser_unsupported ধরে: non-escalatable, সর্বোচ্চ
  environment scope।

স্পষ্ট করে বলি, যা এই session-এ করা হয়নি:

  সিদ্ধান্ত লাগবে।

PHASE 4 (raw-TS ও player lifecycle) — করা হয়নি, এই session-এর তালিকায় ছিল না।
  এখানেই Zee Bangla-র আসল সমাধান: mpegts.Events.LOADING_COMPLETE handle করা,

  pause→unload→detach→destroy→create→attach→load→play, exception গিলে না
  ফেলা, duplicate-burst সুরক্ষা, backoff সহ bounded retry, এবং interlaced /
  no-IDR stream-এর জন্য ভিন্ন handling।

PHASE 5 (২১৫টি movie record) — আলাদা কাজ, পরিকল্পনা অনুযায়ীই বাকি।

CROSS-RUN PERSISTENCE STORE — logic আছে, store নেই।
  persistence_state() পুরোপুরি কাজ করে, কিন্তু scan-এর মাঝে observation
  জমিয়ে রাখার কোনো store নেই, তাই কার্যত এখনো counter এক run-এর বেশি
  এগোতে পারে না। store বানানো মানে নতুন state file লেখা — যা visibility
  বদলাতে পারে, তাই audit-only ধাপে ইচ্ছাকৃতভাবে করা হয়নি।

HMAC KEY — CI-তে নেই।

  record `unknown`. এটি নিরাপদ দিকেই ভুল করে (unknown কিছু hide করতে পারে
  না), এবং correlation/redundancy আলাদা grouping key দিয়ে ঠিকই কাজ করে।

VANTAGE INDEPENDENCE — একবার মাপা, প্রতিষ্ঠিত নয়।
